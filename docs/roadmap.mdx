# Roadmap

Where avuru obs is headed. This is **directional, not a commitment** — scope and
order shift as we learn. The authoritative technical detail lives in the engine
repo's [`ROADMAP.md`](https://github.com/avuruvision/avuru-obs/blob/main/ROADMAP.md);
this page is the human-readable summary. For what already works today, see
[Feature status](/docs/status); for what has shipped, see the
[Changelog](/changelog).

## North star

:::tip The wedge
A fresh Kubernetes cluster → **live service map in under five minutes**, zero app
changes. Every milestone is judged against this, and it's enforced as a CI gate.
:::

## v0.1 — the wedge (released 2026-07-15)

The signal tiers we ship for `0.1`:

| Tier | Signal | Status |
|---|---|---|
| **Full** | Service map + RED metrics; trace explorer (waterfall, search) | <StatusBadge status="shipped" /> |
| **Basic** | Logs (collection, full-text search, `trace_id` correlation) | <StatusBadge status="shipped" /> |
| **Lite** | Continuous profiling (per-service CPU flame graphs) | <StatusBadge status="shipped" /> |
| **Supporting** | Infra metrics (node/pod CPU, memory, network) | <StatusBadge status="shipped" /> |

Plus the hard promise: an **OTLP drop-in replacement** — already-instrumented apps
migrate by changing only the exporter endpoint, no SDK or code changes.

## v0.2 — depth and control (released 2026-07-28)

Everything targeted at v0.2 shipped in
[v0.2.0](/docs/releases): secure-by-default authentication with per-project
roles and OIDC SSO, the module framework (pick your signals), error tracking
with a browser ingest path, service health groups with criticality tiers,
alerting webhooks, network health on the service-map edges, the green
energy & carbon module, and a CI-proven "safe to leave on" sensor. The
project is licensed AGPL-3.0 as of this release. Full detail on the
[feature status](/docs/status) page and in the
[changelog](/changelog/v0-2-0).

## v0.3 — tenancy you can trust (released 2026-07-31)

v0.2 secured the read side; [v0.3.0](/docs/releases) closes the write side.
Projects became something you administer — **create, rename and delete them
from the UI** — and **per-project ingest keys** mean a sender no longer just
claims a tenant: in `enforce` mode the key decides where its telemetry lands.
Alongside that: a **one-click read-only demo**, **green energy on RAPL-less
cloud VMs**, the control-plane groundwork for runtime collection switches, and
the rename of the deploy layer from `avuruops` to **`avuruobs`** (breaking —
see the [upgrade guide](/docs/operations/upgrade)). Full detail on the
[feature status](/docs/status) page and in the
[changelog](/changelog/v0-3-0).

## v0.4 — accounts you can administer (released 2026-08-07)

[v0.4.0](/docs/releases) finishes the account lifecycle v0.2 began: **user
management from the UI** — edit a user's name and role grants, reset a password,
delete an account behind a disable-first rule — plus a **self-service password
change** in Settings → Account, with password operations refused for SSO users
whose credential lives at the identity provider. Reviewing that surface closed
**three ways into an account**: a local password that could be minted on an
SSO-only account, a login lockout that rotating IP addresses walked straight
past, and an SSO login able to take over a local account's email. On the
operations side, an install whose schema migration never ran now **repairs
itself** and reports applied-versus-expected schema in Settings → Status; green
no longer takes the sensor down on nodes without RAPL; and login works behind a
reverse proxy that rewrites `Host`. Full detail on the
[feature status](/docs/status) page and in the
[changelog](/changelog/v0-4-0).

## v0.5 — operate it from the UI (directional)

Almost everything you administer today needs a values edit and a redeploy.
v0.5 closes that gap, so the people who run avuru obs can change it from the
app they are already looking at.

- **Runtime collection control — done.** The applier and the editable Settings →
  Collection UI [have shipped](/changelog/collection-runtime-control): each
  signal switches on or off from the app and the sensor follows in seconds,
  still default-off and still behind a narrowly-scoped Role. OpAMP remains the
  destination: status reporting first, remote-config when the upstream grows a
  client.
- **Service groups from the UI — done.** Health groups and their criticality
  tiers [are now authored in the app](/changelog/service-groups-ui): Settings →
  Groups creates, edits and deletes them, and the change applies to the next
  health read. Chart-declared groups stay read-only and win a name collision,
  and auto-grouping by namespace is unchanged.
- **A real configuration surface:** storage usage, retention and cluster
  topology at a glance; an access view showing which role may do what; the
  identity-provider group mapping made editable; and API tokens for scripts and
  CI.
- **An overview screen, and a topology worth reading:** one page answering "how
  is the estate doing?", plus a clearer service map. Sorting and filtering
  [have arrived](/changelog/nodes-sort-filter) on the Nodes screen.

## Beyond v0.5 (directional)

- **Wider ingest compatibility:** push receivers for the common
  tracing/metrics/logging wire protocols alongside OTLP, plus forwarding
  exporters so avuru obs can dual-write during a migration.
- **More clients:** the hub API is the client-agnostic contract; the SPA is one
  thin client. A **Grafana** data source and a **CLI** are planned, both riding
  v0.5's API tokens.
- **Multi-cluster projects:** member projects that aggregate several clusters,
  per-project retention and system status, and chart component toggles so a
  secondary cluster installs gateway(+sensor)-only against a shared
  ClickHouse. Project CRUD and ingest keys shipped in v0.3.
- **Richer auto-tagging:** map Kubernetes labels/annotations to business tags
  and filter by them across every signal.
- **Storage re-evaluation:** ClickHouse stays behind the `storage.Store`
  interface; GreptimeDB is slated for re-evaluation mid-2027 without changing hub
  code.

## How this roadmap changes

Open an issue or discussion to propose a change of direction; larger items
graduate into an Avuru Enhancement Proposal before implementation. Roadmap edits
go through a normal pull request.
