# avuru obs vs. the alternatives

Most teams already run *something* for telemetry. This section is an honest look
at how **avuru obs** compares to the tools you're most likely replacing — and how
to migrate from each without a rewrite.

Avuru Obs combines traces, logs and metrics in ClickHouse, with eBPF discovery
for supported workloads and OTLP ingestion for existing instrumentation.
CPU profiling is experimental and opt-in. Green, cost, mesh, AI and MCP are
optional; outgoing integrations follow the destinations you configure.

The latest verified public release is **v0.16.0** (7 September 2026).
Some documentation follows development trunk: check [feature status](/docs/status/)
and the [published releases](https://github.com/avuruvision/avuru-obs/releases)
for version-specific availability.

Evaluate the capabilities you actually need with a test service and your
collection pipeline. A backend migration does not automatically move historical
storage, dashboards, alert rules or access policies. Use the
[OTLP adoption guide](/docs/setup/otel-bridge/) to validate a reversible path.

## How migration works, in general

Because avuru obs is a **drop-in OTLP backend**, migrating from any
OpenTelemetry-compatible source is the same three moves:

1. Install avuru obs (`helm install`) alongside what you run today.
2. Repoint your OTLP exporter (or OTel Collector / Grafana Alloy) at the avuru
   `gateway` — `:4318` (HTTP) or `:4317` (gRPC). You can **dual-export** and run
   both in parallel while you validate.
3. Once the data looks right, cut over and decommission the old backend.

Full steps live in the [OTLP bridge guide](/docs/setup/otel-bridge). Each page
below adds the specifics for that tool.
