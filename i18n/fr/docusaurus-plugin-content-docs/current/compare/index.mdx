# avuru obs vs. les alternatives

La plupart des équipes font déjà tourner *quelque chose* pour leur télémétrie. Cette
section porte un regard honnête sur la façon dont **avuru obs** se compare aux outils
que vous êtes le plus susceptible de remplacer — et sur la manière de migrer depuis
chacun sans tout réécrire.

Avuru Obs réunit traces, logs et métriques dans ClickHouse, avec découverte eBPF
pour les workloads pris en charge et ingestion OTLP pour votre instrumentation.
Le profiling CPU est expérimental et optionnel. Green, cost, mesh, AI et MCP
sont optionnels ; les intégrations sortantes utilisent les destinations configurées.

La dernière release publique vérifiée est **v0.16.0** (7 septembre 2026).
Certaines pages documentent le trunk : consultez [l’état des fonctionnalités](/docs/status/)
et les [versions publiées](https://github.com/avuruvision/avuru-obs/releases)
pour connaître la disponibilité dans votre version.

Évaluez vos besoins avec un service de test et votre pipeline de collecte.
Migrer de backend ne transfère pas automatiquement historique, dashboards,
règles d’alerte ou accès. Le [guide OTLP](/docs/setup/otel-bridge/)
propose un parcours réversible à valider.

## En un coup d'œil

| Ce que vous utilisez aujourd'hui | Catégorie | Ce qu'avuru obs change | À lire |
|---|---|---|---|
| **Jaeger** | Tracing distribué | Ajoute les logs (+ métriques/profilage) dans un seul stockage ; carte eBPF sans SDK | [vs Jaeger](/docs/compare/jaeger) |
| **Stack Grafana (Loki/Tempo/Mimir)** | Stack OSS assemblée | Un seul moteur et une seule UI au lieu de quatre systèmes à exploiter | [vs la stack Grafana](/docs/compare/grafana-stack) |
| **Prometheus** | Métriques | Métriques **RED** automatiques corrélées aux traces et logs | [vs Prometheus](/docs/compare/prometheus) |
| **Datadog / New Relic** | APM SaaS commercial | Auto-hébergé, sans agents propriétaires, sans facture par hôte — plus l'énergie & les gCO₂e par service | [vs Datadog](/docs/compare/datadog) |
| **Sentry** | Suivi des erreurs | Incidents dérivés de l'OTLP que vous envoyez déjà, plus un DSN SDK Sentry drop-in — sans facturation par événement | [vs Sentry](/docs/compare/sentry) |
| **GlitchTip** | Suivi des erreurs | Même protocole d'ingestion Sentry, mais des erreurs unifiées avec traces, logs et carte eBPF | [vs GlitchTip](/docs/compare/glitchtip) |
| **DeepFlow** | Plateforme eBPF + ClickHouse | UI first-party complète et suivi des erreurs natif sur la même base eBPF/ClickHouse | [vs DeepFlow](/docs/compare/deepflow) |
| **Coroot** | Plateforme eBPF + ClickHouse | Un seul ClickHouse pour chaque signal, plus le suivi des erreurs comme module de premier plan | [vs Coroot](/docs/compare/coroot) |
| **SigNoz** | Plateforme OTel + ClickHouse | Même base OTel/ClickHouse, plus une carte eBPF sans code, du profilage continu et aucune fonctionnalité bridée | [vs SigNoz](/docs/compare/signoz) |
| **Apache SkyWalking** | APM à agents de langage | Un seul ClickHouse et du SQL universel au lieu de BanyanDB, plus une carte eBPF sans code | [vs SkyWalking](/docs/compare/skywalking) |

## Comment fonctionne la migration, en général

Parce qu'avuru obs est un **backend OTLP drop-in**, migrer depuis n'importe quelle
source compatible OpenTelemetry se fait des trois mêmes gestes :

1. Installez avuru obs (`helm install`) à côté de ce que vous utilisez aujourd'hui.
2. Repointez votre exportateur OTLP (ou OTel Collector / Grafana Alloy) vers le
   `gateway` d'avuru — `:4318` (HTTP) ou `:4317` (gRPC). Vous pouvez
   **double-exporter** et faire tourner les deux en parallèle le temps de valider.
3. Une fois les données validées, basculez et décommissionnez l'ancien backend.

Les étapes complètes sont dans le [guide du pont OTLP](/docs/setup/otel-bridge).
Chaque page ci-dessous ajoute les spécificités de l'outil concerné.
